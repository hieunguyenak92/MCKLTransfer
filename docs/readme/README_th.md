# MCKL Transfer

</div>

แชร์ไฟล์และแชตผ่านเซิร์ฟเวอร์ส่วนตัวใน LAN หรือระหว่างอุปกรณ์ที่ได้รับอนุญาตในเครือข่าย overlay มีเพียงเซิร์ฟเวอร์ที่ต้องใช้ Node.js ส่วนอุปกรณ์อื่นเปิดผ่านเบราว์เซอร์ ไม่มีบัญชีคลาวด์ของ MCKL, analytics, ฐานข้อมูล หรือ dependency ของ npm ที่จำเป็นขณะรัน

**0.2.0-alpha.2 · Apache-2.0 · รุ่นทดลอง** อ่าน[ผลการตรวจสอบ](../VALIDATION.md)และ[โมเดลความปลอดภัย](../../SECURITY.md)ก่อนใช้งาน ยังไม่มีการรับประกันการสนับสนุนแบบเสถียรหรือความเร็ว LAN บนอุปกรณ์ทุกชนิด

## เริ่มต้นในเครือข่ายที่เชื่อถือได้

ติดตั้ง Node.js **24 ตั้งแต่ 24.22.2** หรือ **26 ตั้งแต่ 26.13.0** ที่อัปเดตแพตช์แล้ว จากโฟลเดอร์ซอร์สให้รัน:

```sh
npm start
```

ไม่ต้องใช้ `npm install` เทอร์มินัลจะแสดงที่อยู่ LAN, รหัสเข้าถึง 6 หลัก และ**รหัสผู้ดูแลแยกต่างหาก** เปิดที่อยู่ LAN บนอุปกรณ์อื่น ตั้งชื่ออุปกรณ์ แล้วกรอกรหัสเข้าถึง ให้รหัสผู้ดูแลเฉพาะผู้ที่ดูแลเซิร์ฟเวอร์เท่านั้น รหัสเหล่านี้ไม่ถูกเปิดเผยผ่าน API แม้เข้าจาก localhost

ค่าเริ่มต้นเป็น HTTP ที่ไม่เข้ารหัส ใช้เฉพาะเครือข่ายที่คุณควบคุมและกับผู้ที่เชื่อถือได้ สำหรับการเชื่อมต่อแบบอื่นให้ใช้ HTTPS หรือ overlay ที่จำกัดสิทธิ์ อย่า forward พอร์ตนี้จากเราเตอร์ออกสู่อินเทอร์เน็ต

### วิธีใช้

- เลือกหรือลากหลายไฟล์ได้ คิวร่วมของแอปส่งได้พร้อมกันสูงสุดสองไฟล์ พร้อมความเร็ว เวลาที่คาดว่าจะเสร็จ การพัก การอัปโหลดต่อ การลองใหม่ และการยกเลิก
- หลังเครือข่ายหลุดหรือโหลดหน้าใหม่ ให้เลือกไฟล์เดิมอีกครั้งเพื่ออัปโหลดต่อ ต้องยังมี cookie ของอุปกรณ์และการอัปโหลดยังไม่หมดอายุ เบราว์เซอร์จะไม่เก็บสิทธิ์อ่านไฟล์ให้อัตโนมัติหลังปิดหน้า
- ใช้**แท็บส่งไฟล์เพียงหนึ่งแท็บต่อเซิร์ฟเวอร์** แท็บที่มี origin เดียวกันใช้ cookie และข้อมูลการอัปโหลดต่อร่วมกัน หากสองแท็บอัปโหลดต่อในเซสชันเดียวกัน การยกเลิกในแท็บหนึ่งอาจลบข้อมูลที่ยังไม่เสร็จของอีกแท็บ ไฟล์ต้นฉบับยังปลอดภัย แต่แท็บที่เหลือต้องเริ่มส่งใหม่เมื่อพบ `404` รุ่น alpha ยังไม่ประสานสิทธิ์เจ้าของอัปโหลดระหว่างแท็บ
- ก่อนส่ง เบราว์เซอร์จะอ่านไฟล์ต้นฉบับเพื่อคำนวณ SHA-256 จากนั้น host จะตรวจสอบแต่ละ chunk และไฟล์ที่เสร็จแล้ว การแฮชเพิ่มการอ่านไฟล์อีกหนึ่งรอบและอาจช้าบนอุปกรณ์ที่มีประสิทธิภาพต่ำ แอปไม่เก็บไฟล์ทั้งก้อนไว้ใน RAM
- ไฟล์ที่ส่งเสร็จจะปรากฏในรายการกลาง สมาชิกทุกคนที่เข้าสู่ระบบดาวน์โหลดได้ สมาชิกจะลบได้เฉพาะไฟล์ที่ตนส่ง ส่วนผู้ดูแลลบได้ทุกไฟล์และเพิกถอนเซสชันอุปกรณ์ได้
- แชตกลางเก็บข้อความล่าสุดไม่เกิน 200 ข้อความใน RAM และจะหายเมื่อเริ่ม host ใหม่ เปิดหน้าไว้ระหว่างส่ง โดยเฉพาะบนโทรศัพท์ PWA ไม่รับประกันการส่งเบื้องหลังหรือการอัปโหลดต่อเมื่อ iOS ล็อกหน้าจอ

สถาปัตยกรรมนี้คือ **เบราว์เซอร์ A → host เก็บไฟล์ → เบราว์เซอร์ B ดาวน์โหลด** “อัปโหลดเสร็จ” หมายถึง host ได้รับและตรวจสอบแล้ว ไม่ได้หมายความว่า B ดาวน์โหลดหรือบันทึกไฟล์แล้ว Host อ่านได้ทั้งไฟล์และแชต ยังไม่มี E2EE หรือห้องส่วนตัวแยกตามผู้รับ

## การตั้งค่า

แอปอ่านตัวแปรสภาพแวดล้อมของโปรเซส ไม่โหลด `.env` อัตโนมัติ ขนาดมีหน่วยเป็นไบต์ เวลาเป็นมิลลิวินาที

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `HOST`, `PORT` | `0.0.0.0`, `8787` | อินเทอร์เฟซและพอร์ตที่รับการเชื่อมต่อ ค่าเริ่มต้นเป็น IPv4 |
| `SHARE_DIR` | `./shared` ข้างซอร์ส | โฟลเดอร์ข้อมูลส่วนตัว แนะนำให้อยู่นอก repository |
| `DEVICE_NAME` | hostname | ชื่อ host แสดงหลังเข้าสู่ระบบและในเทอร์มินัลเท่านั้น |
| `SHARE_CODE` | สุ่ม 6 หลักทุกครั้งที่รัน | รหัสสมาชิก ยังคงรองรับ `LAN_SHARE_CODE` เพื่อความเข้ากันได้ |
| `ADMIN_CODE` | สุ่มแยกใหม่ทุกครั้งที่รัน | อย่างน้อย 24 อักขระ ต้องเก็บเป็นความลับ |
| `MAX_FILE_SIZE` | `21474836480` (20 GiB) | ขนาดสูงสุดต่อไฟล์ |
| `MAX_TOTAL_SIZE` | `107374182400` (100 GiB) | ผลรวมไฟล์ที่เสร็จแล้วและขนาดที่จองไว้สำหรับอัปโหลด |
| `MIN_FREE_SPACE` | `134217728` (128 MiB) | พื้นที่ว่างสำรอง ไม่ใช่ disk quota ของ OS |
| `CHUNK_SIZE` | `4194304` (4 MiB) | คำขออัปโหลด chunk แต่ละครั้งรองรับสูงสุด 16 MiB |
| `MAX_CONCURRENT_UPLOADS` | `4` | จำนวนงานเขียน/แฮชอัปโหลดที่ทำพร้อมกันบนเซิร์ฟเวอร์ |
| `MAX_PENDING_UPLOADS` | `128` | จำนวนอัปโหลดที่ยังไม่เสร็จซึ่งเก็บไว้ |
| `UPLOAD_TTL_MS` | `86400000` (24 ชั่วโมง) | กำหนดหมดอายุแบบตายตัวนับจากสร้างอัปโหลดที่ยังไม่เสร็จ |
| `SESSION_TTL_MS`, `MAX_DEVICES` | `43200000` (12 ชั่วโมง), `128` | อายุเซสชันปกติและจำนวนเซสชันอุปกรณ์ทั้งหมด การจดจำอุปกรณ์มีอายุ 30 วัน |
| `REQUEST_TIMEOUT_MS` | `1800000` (30 นาที) | เวลารับคำขอหนึ่งครั้ง ตัด socket ที่ไม่มีกิจกรรม 60 วินาที |
| `TLS_KEY_FILE`, `TLS_CERT_FILE` | ไม่ตั้งค่า | คู่ private key/ใบรับรอง PEM สำหรับ HTTPS โดยตรง |
| `PUBLIC_URL` | ไม่ตั้งค่า | origin ภายนอกของ proxy เช่น `https://transfer.example.org` ห้ามมี path/query |
| `ALLOWED_HOSTS` | hostname/อินเทอร์เฟซในเครื่อง | เพิ่ม hostname/IP เฉพาะ คั่นด้วยจุลภาค ห้ามใช้ wildcard หรือพอร์ต |

ตัวอย่าง PowerShell ที่ใช้โฟลเดอร์ข้อมูลแยก:

```powershell
$env:SHARE_DIR = "D:\MCKL-data"
$env:DEVICE_NAME = "Home transfer host"
npm start
```

รหัสที่เปลี่ยนหลังเริ่มใหม่ไม่เพิกถอนเซสชันที่ออกให้แล้ว ใช้หน้าจัดการอุปกรณ์เพื่อเพิกถอน หาก PIN รั่ว ให้เปลี่ยน PIN **และ**เพิกถอนเซสชันที่ไม่เชื่อถือ Cookie และสิทธิ์เจ้าของไฟล์คงอยู่หลังเริ่มใหม่ การออกจากระบบ/ลบ cookie แล้วจับคู่ใหม่จะสร้างตัวตนใหม่ ผู้ดูแลยังลบไฟล์เก่าได้

## HTTPS และการเชื่อมต่อข้ามเครือข่าย

### HTTPS โดยตรง

จัดหาใบรับรองที่ SAN ตรงกับ hostname/IP ที่ใช้งาน จาก CA ที่อุปกรณ์ทุกเครื่องเชื่อถือ เก็บ key นอกซอร์ส จำกัดสิทธิ์อ่าน แล้วตั้งค่าทั้งสองตัวแปร:

```sh
TLS_KEY_FILE=/secure/mckl/server.key TLS_CERT_FILE=/secure/mckl/server.pem npm start
```

เปิด URL `https://...` ที่ตรงกัน อย่าข้ามข้อผิดพลาดตรวจสอบใบรับรอง ใบรับรองแบบลงนามเองต้องมีกระบวนการติดตั้ง CA ที่เชื่อถือ/ตรวจ fingerprint ผ่านช่องทางที่เชื่อถือได้ แอปยังไม่จับคู่ใบรับรองให้อัตโนมัติ Cookie ของ HTTPS มี `Secure`, `HttpOnly`, `SameSite=Strict`

### กลุ่มส่วนตัวผ่าน Tailscale หรือ WireGuard

ติดตั้ง overlay บนอุปกรณ์ ให้สิทธิ์เฉพาะสมาชิกที่ต้องการ และจำกัดพอร์ตบริการ ยังคงใช้การยืนยันตัวตนของ MCKL ด้วย หากใช้ WireGuard คุณต้องจัดการ key, routing, firewall และ DNS เอง หากใช้ Tailscale ให้ตรวจ policy และเส้นทาง direct/relay ช่วง IP ส่วนตัวไม่ได้พิสูจน์ว่าอุปกรณ์เชื่อถือได้

ทางเลือกหนึ่งสำหรับ HTTPS ใน tailnet คือ [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) เมื่อมีชื่อ DNS ของ host และตั้งค่า HTTPS ใน tailnet แล้ว ให้รัน MCKL บน loopback เท่านั้นโดยใช้ origin นั้น:

```sh
HOST=127.0.0.1 PUBLIC_URL=https://YOUR-HOST.YOUR-TAILNET.ts.net npm start
```

ในอีกเทอร์มินัล:

```sh
tailscale serve --bg http://127.0.0.1:8787
tailscale serve status
```

เปิด HTTPS URL ที่ Serve ออกให้ตรงตามนั้น บริการนี้มีไว้สำหรับ tailnet ให้จำกัด access policy ของคุณ ดูเงื่อนไขและวิธีปิดใน [Serve CLI](https://tailscale.com/docs/reference/tailscale-cli/serve) MCKL ไม่ติดตั้งหรือตั้งค่า Tailscale อัตโนมัติ และยังไม่ได้ทดสอบบน tailnet จริงในการเผยแพร่ครั้งนี้

Reverse proxy อื่นต้องส่งต่อ stream/SSE โดยไม่ buffer คง Host เดิมหรือตั้ง `PUBLIC_URL` ให้ถูกต้อง ตั้ง timeout/ขนาด body ให้เหมาะสม และจำกัดการเข้าถึง upstream ให้เฉพาะ proxy ที่เชื่อถือ แอปไม่เชื่อ `X-Forwarded-*` ในการตัดสินความปลอดภัยของการเชื่อมต่อ

## ข้อมูล การอัปเกรด และการสำรองข้อมูล

Host เก็บ `.mckl-manifest.json`, `.mckl-devices.json` (hash ของ token เซสชัน), `.mckl-uploads.json` และ `.mckl-objects/` ใน `SHARE_DIR` ข้อมูลไฟล์ใหม่เก็บตาม ID ส่วนชื่อที่แสดงอยู่ใน manifest อย่าแก้ไขหรือลบไฟล์ภายในขณะเซิร์ฟเวอร์ทำงาน อย่ารันสองโปรเซสบน `SHARE_DIR` เดียวกัน

หยุด host ก่อนสำรองโฟลเดอร์ข้อมูล**ทั้งหมด** Backup มีไฟล์และสิทธิ์เข้าถึงของกลุ่ม จึงต้องได้รับการปกป้อง รุ่น alpha อ่าน manifest ของ MVP เก่าที่อ้างถึง regular file ที่ถูกต้องได้ แต่ไม่ย้ายข้อมูลไฟล์เก่าไป object storage ให้อัตโนมัติ ไฟล์เก่าที่ไม่มีเจ้าของลบได้เฉพาะผู้ดูแล สำรองข้อมูลก่อนอัปเกรด ไม่รองรับการ downgrade หลังจากเขียน manifest รูปแบบใหม่แล้ว

ใช้เฉพาะ filesystem ภายในเครื่องที่เชื่อถือได้และกำหนด ACL อย่างเข้มงวด อัปโหลดที่ยังไม่เสร็จและหมดอายุจะถูกล้าง แต่ไฟล์ที่เสร็จแล้วจะไม่ถูกลบอัตโนมัติ ยังไม่ได้ตรวจสอบ network drive, การซิงก์โฟลเดอร์ข้อมูลขึ้นคลาวด์, ไฟดับจริง หรือความเสียหายของอุปกรณ์จัดเก็บข้อมูล Atomic rename/fsync ไม่ใช่การรับประกันว่าจะป้องกันความเสียหายทุกแบบ

## หากอุปกรณ์อื่นเชื่อมต่อไม่ได้

เลือก IPv4 LAN URL ที่แสดงในเทอร์มินัล ใช้ Wi-Fi เดียวกันและหลีกเลี่ยง guest/AP isolation ตรวจ firewall ให้เปิดพอร์ตเฉพาะเครือข่าย/อุปกรณ์ที่ต้องใช้ ตรวจ health จากอีกเครื่องโดยแทนที่อยู่ตัวอย่าง:

```sh
curl --connect-timeout 5 http://192.168.1.10:8787/api/health
```

คำตอบที่ถูกต้องคือ `{"ok":true}` หาก timeout มักต้องตรวจ routing/firewall หากได้ `403` ให้ตรวจ hostname/Origin และ `ALLOWED_HOSTS`/`PUBLIC_URL` อย่าเพิ่ม wildcard เพื่อแก้ปัญหา เบราว์เซอร์อาจขอสิทธิ์เข้าถึงเครือข่ายภายใน

## การพัฒนา ทดสอบ และเผยแพร่

```sh
npm run check
npm test
npm run release:check
npm run release:source
```

ตัวส่งออกซอร์สรับเฉพาะรายการที่อนุญาต ตรวจ archive ซ้ำ และเขียน SHA-256 ใน `release/` อย่า ZIP โฟลเดอร์ที่ใช้งานอยู่ทั้งหมด `.gitignore` ไม่ตัดไฟล์ออกจาก ZIP ของ Finder และไม่ลบข้อมูลที่ commit แล้ว คง `private: true` เพื่อป้องกันการ publish npm โดยไม่ตั้งใจ ซอร์สยังอยู่ภายใต้ Apache-2.0
